# Каталог, баннеры и доступность оформления

Обновление идёт из `feature/catalog-tags-20261119` в `staging` через отдельный PR. Не выполняет миграций, импорта, изменения товаров, цен, фотографий, покупателей или заказов. Секреты и данные рабочей Neon не нужны для сборки/CI.

## Почему оформление было закрыто

На опубликованной версии `/api/session/` возвращал `checkout_enabled: false`. В Render отсутствовал `STAGING_PICKUP_ENABLED`, `MINIAPP_ORDERS_ENABLED` и `TELEGRAM_NOTIFICATIONS_ENABLED` были выключены, `TELEGRAM_ADMIN_CHAT_ID` не был задан. Это штатный защитный режим, а не поломка сохранения заказов. Новый UI не обходит серверные проверки.

После разрешения владельца в Render → **bolshoy-myasnoy-staging → Environment → Edit**:

| Ключ (скопировать точно) | Значение |
|---|---|
| `STAGING_PICKUP_ENABLED` | `1` |
| `MINIAPP_ORDERS_ENABLED` | `1` |
| `TELEGRAM_NOTIFICATIONS_ENABLED` | `1` |
| `TELEGRAM_ADMIN_CHAT_ID` | Числовой ID ранее проверенной закрытой группы |

`MINIAPP_ORDERS_ENABLE` без последней `D` не используется. Существующие `TELEGRAM_BOT_TOKEN`, `DATABASE_URL`, ключи фотографий и `DJANGO_SECRET_KEY` оставить прежними. Три флага уже имеют `sync: false` в Blueprint; это обновление их не меняет. Кнопка сохранения Environment может сразу перезапустить/развернуть сервис: нажимать только в согласованное окно. Если нужно отдельно проверить интерфейс до открытия заказов, оставить флаги выключенными до контрольного прохода.

Никаких ограничений по отдельному Telegram ID нет. Для заказа нужен авторизованный пользователь с подлинным initData; вход в обычном браузере без этих данных остаётся гостевым. Доставка и онлайн-оплата не включаются.

## Что меняется

- Один существующий баннер заполняет три слайда без копирования файла или записей в базе. Есть свайп и три индикатора. Будущие опубликованные записи Django Admin → «Баннеры» займут соответствующие позиции в своём порядке; недостающие позиции используют первый баннер. Показывается максимум три.
- Касание не добавляет красную рамку. Клавиатурная навигация сохраняет видимый нейтральный фокус; выделение выбранных тегов и ошибки ввода остаются заметными.
- «Помощь» использует существующие SVG-иконки Lucide; системный маркер раскрытия скрыт и заменён SVG-chevron.
- Теги используют существующие категории и названия товаров. Правила находятся в `shop/catalog_tags.py`; они не создают категории/товары и не требуют миграций. В каждой из трёх наполненных групп предусмотрено шесть тегов. API выдаёт только непустые теги текущей категории. Проверяется тип товара в начале названия: арахис со вкусом креветки не становится креветками. Отдельные категории сыров, копчёной/замороженной рыбы не присоединяются ради наполнения тегов. Существующий общий показ молочной группы и сыров сохранён.
- Выбирается один тег, «Все» его снимает. Поиск, единица продажи, доступность и сортировка сочетаются с тегом. Новый выбор начинает с первой страницы; возврат назад восстанавливает ранее загруженную выдачу. Справа есть затухание только пока остались скрытые теги.

## Публикация и ручная проверка

1. В PR дождаться зелёных проверок GitHub Actions. Только после разрешения владельца нажать **Merge pull request → Confirm merge** в `staging`.
2. Render автоматически собирает обновление из `staging`. Дождаться статуса **Live**; рабочую Neon не переключать и повторный импорт не запускать.
3. Полностью закрыть и заново открыть Mini App из `@bmmsev_bot`. Проверить главную (три слайда), «Помощь», три категории, поиск с тегом, «Все», «Показать ещё» и возврат из товара. На iPhone 13 проверить свайп тегов/баннеров, исчезновение затухания в конце и отсутствие красной рамки при касании, клавиатуру и нижнее меню.
4. После настройки Environment проверить `/api/session/`: `checkout_enabled` должен стать `true`. На самом iPhone проверить подлинный Telegram-вход и прежний профиль. Не публиковать initData/Authorization в скриншотах и логах.
5. Для согласованного контрольного заказа проверить сохранённый телефон, состав/цены, явно написать «КОНТРОЛЬНЫЙ ЗАКАЗ — НЕ СОБИРАТЬ» в комментарии, подтвердить один раз. Сверить номер в подтверждении, истории и сообщении закрытой группы. Это создаёт настоящий заказ: заранее согласовать со сотрудниками. Номер и статус должны оставаться после повторного открытия Mini App.
6. При ошибке Telegram заказ остаётся в Admin и истории. Использовать штатные действия «Уведомлений о заказах» из [инструкции](retail-orders-release.md#если-telegram-не-принял-уведомление); не отправлять повторно уже доставленные сообщения. Для быстрого закрытия оформления установить `STAGING_PICKUP_ENABLED=0`.

## Проверки перед PR, 19 ноября 2026

- Django: 130 тестов, один тест конкурентных запросов пропущен на SQLite; отдельно 62 теста PostgreSQL, включая конкурентное оформление, аккаунты, уведомления, рецепты и новые теги, прошли полностью.
- Frontend: 51 тест, TypeScript и production build прошли. Проверка границ публикуемых файлов и `makemigrations --check --dry-run` прошли, новых миграций нет.
- Локальный браузер: 320/360/390/430 px, три категории, одна строка тегов с touch-прокруткой и исчезновением маски, фильтрация, пагинация, возврат из товара, поиск и сброс «Все». Проверены карусель, SVG-маркеры «Помощи», касание и клавиатурный фокус.
- Изолированная QA PostgreSQL с фиктивным токеном: сохранение телефона и восстановление после перезагрузки, подстановка телефона в оформление, сохранение корзины при HTTP 500, один явно помеченный QA-заказ при двойном нажатии, подтверждение/история после перезагрузки. Ошибки Telegram проверены серверными тестами с подменённым API; реальные сообщения в группу не отправлялись.

Эмуляция браузера и автоматизированные проверки не заменяют проверку iOS Safari/Telegram WebView на настоящем iPhone. До публикации результат на Render не считается проверенным.
