# Компактный самовывоз и подтверждение только клавиатурой

Ветка от staging `37c16ab`, после PR №6/7. Новых моделей, миграций, библиотек и изменений правил самовывоза нет. Рабочая Neon, цены, фотографии, бот и Render не изменялись.

## Изменения

В `/checkout` одно компактное поле открывает нижний нативный modal dialog: горизонтальная строка восьми дат, два вертикальных scroll-snap барабана, «Выбрать время». Только эта кнопка сохраняет выбор; закрытие, Escape и Telegram Back оставляют прежнее значение. Повторное открытие восстанавливает его.

Часы берутся только из доступных API slots. Минуты — 00/30; недоступная комбинация при прокрутке заменяется ближайшим фактическим слотом выбранного часа. При смене дня сохраняется ближайшее допустимое время. Закрытые дни, ошибки и истечение слотов обрабатываются без очистки корзины. График и время сборки не дублируются во frontend. Клавиатура скрывается перед открытием; используются существующие Telegram/visual viewport/safe area переменные. Есть клавиатурное управление, reduced motion и fallback для scrollend старых WebView.

Прежняя атомарная схема NEW → CONFIRMED, allowlist, инициатор/nonce/TTL, секрет webhook, проверки чата/бота/message_id, аудит и outbox сохранены. На всех стадиях вызывается только `editMessageReplyMarkup`. В клавиатуре нет имён сотрудников; поля аудита остаются в Admin. После принятия: **✅ Заказ принят · 10:00** (фактическое accepted_at по Москве) и прежняя ссылка Admin. Нажатие индикатора отвечает «Заказ уже принят», не меняет статус повторно. Сбой редактирования не отменяет сохранение; Admin повторяет обновление той же клавиатуры. Текст и части старого outbox не меняются, дополнительные сообщения не отправляются. Mini App использует прежний API и polling: «✅ Ваш заказ принят!».

## Почему отсутствует кнопка

Read-only проверка 21.11.2026: getMe подтвердил @bmmsev_bot, getWebhookInfo вернул отсутствие webhook и одно ожидающее обновление. Настройки не менялись; getUpdates не вызывался. Отсутствие другого getUpdates-процесса этим методом доказать нельзя.

`notification_markup` добавляет кнопку только при `TELEGRAM_ORDER_WEBHOOK_ENABLED=1`, только в последней части уведомления. По умолчанию флаг выключен. Доступа к текущему Render Environment у этой проверки нет: значение на Render нужно проверить владельцу. Включение флага не устанавливает webhook и не добавляет кнопки в уже доставленные сообщения.

## Действия владельца после разрешённого релиза

1. Дождаться зелёного CI, затем только по разрешению выполнить Merge в staging. Render штатно соберёт обновление. Новых миграций нет. Текущие флаги заказов, DATABASE_URL, токен, Django secret и storage не менять.
2. Render → bolshoy-myasnoy-staging → Environment: добавить/проверить `TELEGRAM_WEBHOOK_SECRET` (случайные 32–256 латинских букв, цифр, `_`, `-`) и `TELEGRAM_ORDER_STAFF_IDS` (положительные числовые Telegram ID сотрудников через запятую). Свой ID можно взять в Admin → Покупатели после входа в Mini App. Username и ID группы не подходят. Секрет создать в менеджере паролей; не присылать в чат.
3. Проверить `MINIAPP_PUBLIC_URL=https://bolshoy-myasnoy-staging.onrender.com` и, для ссылки Admin, такой же `MINIAPP_ADMIN_URL`. Сохранить существующие `TELEGRAM_BOT_TOKEN` и `TELEGRAM_ADMIN_CHAT_ID`. Пока `TELEGRAM_ORDER_WEBHOOK_ENABLED=0`.
4. Проверить прежние интеграции/getUpdates. Если другой получатель есть, сначала согласовать интеграцию с ним. Отдельно разобраться с одним ожидающим обновлением через прежнего получателя. Не сбрасывать очередь и не запускать getUpdates ради обхода защиты команды.
5. Бесплатная одноразовая настройка с Windows: в существующий приватный `.env.staging` вне GitHub внести те же secret/staff IDs/постоянный URL, не меняя токен. Выполнить:

```powershell
Set-Location 'C:\Users\Gor Sahakyan\Desktop\bolshoy-myasnoy\.worktrees\pickup-sheet'
$env:MINIAPP_SERVER_ENV_FILE='C:\Users\Gor Sahakyan\Desktop\bolshoy-myasnoy\.env.staging'
& 'C:\Users\Gor Sahakyan\Desktop\bolshoy-myasnoy\.venv-staging\Scripts\python.exe' manage.py check_order_webhook --settings=config.settings_bot_setup
```

Это только getMe/getWebhookInfo; показанные флаги относятся к локальному файлу, не к Render. БД принудительно SQLite в памяти, без подключения к Neon. Токен, secret и список ID не выводятся.

6. Только после отдельного согласования настройки бота, проверки отсутствия другого потребителя и решения вопроса с очередью повторить команду с `--apply --acknowledge-no-other-consumer`. Она регистрирует HTTPS `/api/telegram/order-webhook/`, secret header и только callback_query, не сбрасывая updates. При чужом webhook/необработанной очереди команда остановится. Меню Mini App не меняется.
7. В Render установить `TELEGRAM_ORDER_WEBHOOK_ENABLED=1`, сохранить и дождаться перезапуска. Такой же secret и staff IDs обязательны. Создать согласованный контрольный заказ: первый клик сохраняет NEW, «Отмена» возвращает начальную кнопку, «Да, всё верно» тем же сотрудником сохраняет CONFIRMED. Проверить индикатор времени, неизменность текста и статус покупателя.
8. Для уже доставленного NEW-заказа: Admin → Заказы → выбрать один → «Добавить кнопки подтверждения в доставленное сообщение». Для сбоя клавиатуры: «Принятие заказов и обновление сообщений» → «Повторить обновление…». Не пересылать заказ ради добавления кнопок.

Ранее добавленный старой версией текст о сотруднике автоматически не удаляется: это потребовало бы запрещённого текущей задачей редактирования текста. Обновляется только клавиатура.

Протокол: [editMessageReplyMarkup](https://core.telegram.org/bots/api#editmessagereplymarkup), [setWebhook](https://core.telegram.org/bots/api#setwebhook).

## Проверки

Серверные тесты покрывают pickup_at, идемпотентность, старые заказы, секреты/права/чат/сообщение, обе стадии и отмену, повторы и конкурентные нажатия, отказ Telegram и повтор клавиатуры. Проверяется отсутствие editMessageText/sendMessage при принятии, неизменность payload и аудит.

Локальный браузер с тестовыми API: 320/360/390/430, горизонтальный короткий экран и desktop, safe areas, прокрутка/snap, клавиатура/Telegram Back, смена даты, недоступная комбинация, сохранение/отмена выбора, ошибки/устаревание календаря, сохранение заявки и обновление статуса. Настоящие iOS/Android и рабочая группа требуют ручной проверки после разрешённой публикации/настройки. Реальных заказов при разработке не создавалось.
