# Сессия покупателя и общая корзина

## Причина и восстановление входа

Раньше каждый приватный запрос повторно предъявлял `Telegram.WebApp.initData`, а fetch использовал `credentials: omit`. После часа подпись оставалась подлинной, но `auth_date` уже истёк; после reload SDK также мог не предоставить launch data. Серверной сессии покупателя не существовало. Отсутствие launch data теперь не считается выходом: сначала читается действующая cookie-сессия.

Первый вход: `/api/session/` выдаёт CSRF-токен; `/api/session/login/` принимает подписанный initData и проверяет прежний HMAC и срок, затем меняет ключ Django-сессии и CSRF-токен. Дополнительное чтение подтверждает, что браузер сохранил cookie. Ни `initDataUnsafe`, ни localStorage не используются для авторизации. Сессия хранится в существующей таблице `django_session` PostgreSQL; в отдельной cookie `bm_customer` только случайный ключ. Cookie Django Admin не используется и не заменяется. В staging customer-cookie имеет HttpOnly, Secure и SameSite=Lax без Domain. Все операции по cookie проверяют CSRF и Origin; начальный вход тоже защищён CSRF. Токен CSRF остаётся только в памяти страницы.

По умолчанию сессия действует 14 дней. Необязательный серверный `MINIAPP_SESSION_AGE` задаётся в секундах (от 3600 до 2592000); обычные чтения срок не продлевают. Новый проверенный Telegram-вход может создать новый срок. Возраст initData не отключён и не увеличен. При истечении cookie нужен новый подлинный вход из бота. Старый initData не может продлить сессию. Сетевой сбой сохраняет уже полученный профиль и показывает повтор проверки, не выдаёт ложный выход. Секрет Django и домен при обновлении менять нельзя. При блокировке cookie показывается явная ошибка; фиктивный вход не подставляется.

Старые клиенты с действительным заголовком `Authorization: tma ...` продолжают работать в пределах прежнего срока initData. Эти запросы используют явные подписанные credentials, а не ambient cookie. Они не получают бессрочный обход проверки.

## Корзина

`CustomerCart` — одна запись на Customer (уже уникальный Telegram ID), версия и JSON со связью ID товара → Decimal-количество. Цены и фотографии не копируются в корзину, читаются из каталога. `CartOperation` хранит UUID и отпечаток мутации: повтор после потерянного ответа не применяет её заново.

Новые `/api/cart/` GET/POST определяют покупателя на сервере; передать чужой ID для выбора корзины нельзя. Изменения блокируют строку Customer в PostgreSQL. Версия и ожидаемые количества разрешают независимые изменения разных товаров; конкурирующие правки одного товара дают 409 со свежим снимком. Клиент сохраняет свой черновик и предлагает явно применить локальные изменения поверх свежих данных либо загрузить серверную корзину. Подтверждение всё равно проверяет версию повторно.

Старая гостевая корзина объединяется с серверной по максимальному количеству одного товара, а не суммой: повторное открытие не удваивает одинаковые позиции. Применение записано идемпотентной операцией; источник удаляется только после подтверждения. Неотправленный черновик и операция сохраняются на устройстве под отдельным ключом покупателя, без auth-токенов. Гостевая localStorage-корзина остаётся отдельной. Потеря сети, загрузка страницы и отсутствие входа не отправляют очистку серверной корзины. Изменение цены/шага каталога не превращается в скрытое удаление строки.

Сохранение объединяется короткой задержкой; видимые страницы обновляют корзину каждые 5 секунд, при фокусе, восстановлении сети и возврате из фона. Это HTTP-синхронизация, без платных сервисов и фонового worker. Перед оформлением клиент дожидается синхронизации. Заказ сохраняется прежней транзакцией, затем в ней убираются только соответствующие позиции с теми же количествами; чужие одновременные добавления сохраняются. Ошибка заказа ничего не очищает. Повтор уже сохранённого заказа не очищает новую корзину. Уведомления выполняются после commit прежним механизмом.

## Миграция и публикация

Нужна **0011_customercart_cartoperation**: создаёт только две новые таблицы и их ограничения. Существующие товары, категории, покупатели, заказы, фотографии и импорт не меняются. Таблица Django-сессий уже существует. На отдельной QA PostgreSQL проверены применение 0011 и неизменность контрольных сумм всех 30 прежних бизнес-таблиц (11 014 строк, включая ID и связи). Это проверка QA-копии, не резервная копия актуальной рабочей Neon.

1. Перед разрешённым релизом создать свежую резервную копию действующей Neon существующим процессом из `retail-orders-release.md`. Старую копию не считать актуальной для новых заказов. Не выполнять повторный импорт SQLite.
2. Дождаться зелёного CI PR, затем только с разрешения владельца выполнить Merge в `staging`. Существующий Render автоматически соберёт одну версию frontend/backend и применит 0011 штатным `migrate` при запуске. Не менять `DATABASE_URL`, секрет Django, токен бота, флаги заказов или настройки фотографий.
3. На каждом тестовом устройстве один раз закрыть Mini App и открыть из меню `@bmmsev_bot`, чтобы первоначально создать новую защищённую сессию. После этого проверить reload без initData, закрытие/открытие, телефон и историю.
4. На настоящих iPhone 13 и компьютере: добавить два товара, изменить количество на другом устройстве, вернуться в корзину, проверить синхронизацию и конфликт. Затем согласованный контрольный заказ с явной пометкой; проверить историю, уведомление и очистку соответствующих строк. Автоматическая эмуляция не доказывает поведение конкретного iOS WebView.
5. При откате кода новые таблицы не удалять и миграцию не обращать: серверные корзины останутся в PostgreSQL, но старая версия интерфейса ещё использует локальную корзину. Исправление выполняется новым релизом, а не восстановлением старой базы поверх новых заказов.

Временные Cloudflare URL для размещённого приложения не нужны. Обычный Vite proxy сохраняет Host для same-origin CSRF; старый live gateway передаёт только cookie `bm_customer` и `csrftoken`, соответствующие Set-Cookie, Origin и X-CSRFToken через свой существующий список разрешённых маршрутов/хостов. Cookie Django Admin и произвольные cookie не передаются. Защита Host/CORS глобально не отключается. Для ручной уборки истёкших Django-сессий доступна штатная `clearsessions`; постоянный background-процесс не требуется.

## Выполненные проверки

- 17 проверок сессии и корзины на отдельной PostgreSQL: подпись, срок, CSRF, cookie, изоляция Admin и покупателей, идемпотентность, весовые количества, очистка только после заказа, параллельные изменения с блокировками строк.
- 90 frontend-тестов, проверка TypeScript и production build: в том числе восстановление cookie, истёкший initData, сетевые ошибки, сохранение черновика, повтор потерянного запроса и запоздавший ответ после заказа.
- 16 сценариев в двух независимых браузерных контекстах с отдельной QA PostgreSQL: перенос гостевой корзины, синхронизация, reload и повторное открытие без initData, телефон, конфликт, offline/reconnect, история и контрольный QA-заказ. Использовались синтетические подписанные данные и отключённые уведомления; рабочие заказы и Telegram-группа не затрагивались.

Эмуляция мобильной ширины не заменяет проверку настоящего Telegram на iPhone 13. Проверки публикации на Render выполняются только после разрешённого релиза.
