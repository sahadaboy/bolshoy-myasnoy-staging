# PR B: желаемое время самовывоза и принятие сотрудником

Независим от PR A. Существующие аккаунты, cookie-сессии, каталог, цены, фотографии, корзина и статусы сохраняются. Работающая Neon и настройки бота при подготовке не менялись. Новый webhook по умолчанию выключен.

## График и оформление

Источник после преобразования — интервалы StoreProfile по дням недели, редактируемые в Admin → «О нас и контакты». День без интервалов закрыт; можно задать несколько непересекающихся интервалов. Там же время на сборку: по умолчанию 60 минут, допустимо 1–1440. «О нас» получает текст из этих же интервалов, а не из копии frontend.

Проверка действующей конфигурации выполнена только чтением: понедельник/вторник/четверг/пятница/суббота/воскресенье 08:00–20:00, среда 08:00–19:00. Миграция использует фактический текст каждой базы: только семь однозначных ежедневных строк преобразуются автоматически. Неоднозначный текст сохраняется, структурированный график не включается, выдача слотов блокируется до настройки Admin. Старое текстовое поле остаётся для совместимости/отката, но после включения не определяет часы.

`/api/pickup-slots/`: московская дата сегодня и следующие семь дней включительно (всего восемь), сетка 30 минут, начало интервала не раньше server now + время сборки. Время закрытия не является доступным временем получения. Нет предположений об остатках или автоматической готовности.

Новые заказы требуют timezone-aware `pickup_at`; сервер повторно проверяет график, срок сборки, сетку и горизонт непосредственно в транзакции. Дата включена в fingerprint, эквивалентные часовые пояса нормализованы. Идентичный повтор возвращает прежний заказ; другое время с тем же ключом — 409. Старый уже сохранённый запрос без времени можно повторить; новый запрос из старой открытой вкладки получает понятный 400 с просьбой обновить оформление. Его корзина не очищается.

Успех показывается только после ответа о сохранённом заказе: `/profile/orders/<uuid>/success`. Перезагрузка читает тот же приватный API. В деталях/истории есть желаемое время; NEW ожидает оператора, CONFIRMED показывает принятие. Открытый экран проверяет сервер каждые 12 секунд, при возврате/восстановлении сети; в фоне и после завершения polling остановлен. Полученные данные сохраняются при временной ошибке. Это не push на закрытый телефон.

## Telegram и надёжность

Новые уведомления — экранированный HTML, без адреса, с заметным временем, составом, суммой, временем оформления, необязательным комментарием и предупреждением для весовых товаров. Части ограничены 3500 UTF-16 единицами с запасом для принятия. Длинный текст не режет HTML-теги. Ранее подготовленные plain payload, назначение и подтверждённые ID сообщений не переписываются.

Подтверждение находится на последней части полного уведомления, Admin доступен на всех частях. Первое нажатие меняет только кнопки. Второе требует того же Telegram ID сотрудника и одноразового nonce; срок шага — пять минут. «Отмена» возвращает исходные кнопки без смены статуса. Членства в группе недостаточно: нужен серверный список ID. Проверяются секрет HTTPS webhook, бот, сохранённый чат, исходный message_id и случайный токен заказа. Повторы updates/callbacks записываются и не принимают заказ повторно. Неизвестные обновления чужих функций не подтверждаются HTTP 200.

NEW → CONFIRMED и история статуса сохраняются атомарно с Telegram ID/username/именем/временем сотрудника. Затем редактируется исходное сообщение. Текст берётся из сохранённого payload, поэтому «ЗАКАЗ ПРИНЯЛ» не накапливается при повторе. Сбой Telegram не отменяет принятие в БД; состояние редактирования и ошибка остаются в Admin → «Принятие заказов и обновление сообщений» → «Повторить обновление…». Это редактирование, а не новая отправка. Зависшая попытка освобождается по lease через 60 секунд; бесконечного фонового процесса нет.

Для старых уже доставленных NEW-заказов: Admin → Заказы → выбрать один → «Добавить кнопки подтверждения в доставленное сообщение». Состав сообщения сохраняется, повторная отправка не выполняется. Для недоставленных частей сначала завершить существующую доставку. Не отменять ручную проверку доставки у статуса uncertain старого outbox.

## Миграции и проверка

- `0012_pickup_schedule_and_acceptance`: добавляет nullable `Order.pickup_at`, настройки графика, формат старого outbox и новые таблицы интервалов, принятия и receipts. Удалений существующих таблиц/строк нет.
- `0013_convert_explicit_store_hours`: заполняет только новые интервалы/флаг при однозначном старом расписании. Исходные поля, заказы и фотографии не изменяются.
- На существующей изолированной QA PostgreSQL сравнивались исходные колонки до/после: 33 таблицы, 11 034 строки, включая ID, связи, корзины и django_session — контрольные суммы совпали. Все старые pickup_at пустые, преобразованы семь интервалов. Отчёт `.runtime/pickup-migration-verification.json` локальный; это не резервная копия действующей Neon.
- Серверные проверки покрывают даты, закрытые дни, разные интервалы, Москву/полночь, повторную проверку времени, подмену, старые заказы, fingerprint, HTML/длинные уведомления, оба шага/отмену/срок/чужого сотрудника, конкурентное принятие, ошибки Telegram/БД и восстановление редактирования. На QA PostgreSQL отдельно прошли 58 проверок вместе с прежними заказами/корзиной, включая реальные гонки блокировок.
- Frontend: 103 теста, TypeScript/build, 17 локальных браузерных проверок с тестовым API: 320/360/390/430, часовой пояс устройства Auckland, обязательный выбор, отсутствие слотов/ошибка/retry, клавиатура, успех/reload, 12-секундное обновление, фон и временная ошибка. Реального Telegram-клиента или отправки в рабочую группу эти проверки не заменяют.

## Согласованное подключение: без платных сервисов

На момент read-only проверки @bmmsev_bot webhook отсутствовал, было одно ожидающее обновление. API не позволяет доказать отсутствие чужого getUpdates-процесса. Ничего не отключалось, очередь не читалась/не сбрасывалась. Поэтому автоматической установки при deploy нет.

После разрешённого релиза:

1. До Merge B сделать свежую резервную копию рабочей Neon существующим процессом из `retail-orders-release.md`. Дождаться зелёного CI. Merge выполняется только по разрешению владельца; штатный Render затем применит 0012–0013. Не менять DATABASE_URL, секрет Django, фотографии, токен бота или текущие флаги заказов.
2. Проверить график и 60 минут в Admin. При `schedule_configured=False` явно настроить часы/закрытые дни и включить структурированный график. Проверить интервалы в форме без отправки заявки.
3. Отдельно согласовать настройку бота. Проверить существующие обработчики/getUpdates и корректно обработать прежнее ожидающее обновление. Команда откажется заменить чужой webhook или начать с необработанной очередью. Не удалять webhook и не использовать drop_pending_updates ради обхода проверки.
4. В Render Environment добавить `TELEGRAM_WEBHOOK_SECRET` — случайный секрет 32–256 символов (латинские буквы, цифры, `_` и `-`), и `TELEGRAM_ORDER_STAFF_IDS` — числовые ID разрешённых сотрудников через запятую. Секрет создать в менеджере паролей, не присылать в чат. Сохранить действующий TELEGRAM_ADMIN_CHAT_ID закрытой группы и MINIAPP_PUBLIC_URL постоянного магазина. Пока `TELEGRAM_ORDER_WEBHOOK_ENABLED=0`.
5. Для одноразовой настройки можно использовать Windows, без консоли Render. В локальный приватный `C:\Users\Gor Sahakyan\Desktop\bolshoy-myasnoy\.env.staging` добавить те же секрет/ID и постоянный URL. Не публиковать этот файл. Затем:

```powershell
Set-Location 'C:\Users\Gor Sahakyan\Desktop\bolshoy-myasnoy\.worktrees\pickup-confirmation'
$env:MINIAPP_SERVER_ENV_FILE='C:\Users\Gor Sahakyan\Desktop\bolshoy-myasnoy\.env.staging'
& 'C:\Users\Gor Sahakyan\Desktop\bolshoy-myasnoy\.venv-staging\Scripts\python.exe' manage.py check_order_webhook --settings=config.settings_bot_setup
```

Это только getMe/getWebhookInfo. Настройки `settings_bot_setup` принудительно используют SQLite в памяти и не подключаются к Neon, даже если приватный файл содержит DATABASE_URL. Токен в аргументах/выводе отсутствует.

6. Только после отдельного разрешения и проверки отсутствия других потребителей/ожидающих обновлений выполнить ту же команду с `--apply --acknowledge-no-other-consumer`. Она устанавливает HTTPS `/api/telegram/order-webhook/`, secret header и только callback_query, без сброса очереди. Меню Mini App не меняется. Если обнаружен другой обработчик, требуется интеграция с ним, а не замена.
7. В Render включить `TELEGRAM_ORDER_WEBHOOK_ENABLED=1`. Теперь новые уведомления имеют кнопки. Создать помеченный контрольный заказ: первый клик не меняет NEW, отмена сохраняет NEW, второй клик инициатора меняет CONFIRMED; проверить текст и заказ в профиле. Для прежнего сообщения при необходимости использовать действие Admin.

При откате кода после появления новых заказов не откатывать/удалять таблицы и поля. Старые времена и принятые заказы должны остаться в PostgreSQL. Webhook перед отключением/сменой согласовывается отдельно; не подменять его другим потребителем автоматически.

## Образец сообщения (тестовые данные, не реальный заказ)

```text
🛒 НОВЫЙ ЗАКАЗ
№ БМ-ТЕСТ-001

📅 Забрать: 22.11.2026 в 14:30

👤 Покупатель: Анна
📞 Телефон: +7 (000) 000-00-00

📦 Состав заказа
• Хлопья Myllyn Paras 500 г — 4 шт. — 531,96 ₽

💰 Итого: 531,96 ₽

🕒 Заказ оформлен: 21.11.2026 в 09:55
```

После принятия исходный текст сохраняется, в его конец добавляется (жирным в Telegram):

```text
✅ ЗАКАЗ ПРИНЯЛ: @employee
🕒 Заказ принят в 21.11.2026 10:00
```

Фактический сотрудник и время берутся из сохранённого принятия, а не из примера. При отсутствии username используется экранированное отображаемое имя. В группе не появляется отдельное сообщение о принятии.

Официальный протокол: [setWebhook/secret_token](https://core.telegram.org/bots/api#setwebhook), [callback_query](https://core.telegram.org/bots/api#callbackquery), [editMessageText](https://core.telegram.org/bots/api#editmessagetext).
