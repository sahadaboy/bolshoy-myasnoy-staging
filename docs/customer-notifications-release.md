# Личные уведомления о принятии заказа

Ветка от staging `09458d7` после PR №8. Интерфейс, Telegram-авторизация, каталог, фотографии, webhook, BotFather и группа сотрудников не меняются. При разработке реальные личные сообщения не отправлялись; рабочая Neon и Render не изменялись.

## Поведение

Только окончательное «Да, всё верно» создаёт `CustomerOrderNotification` типа `ORDER_CONFIRMED` в той же транзакции, что NEW → CONFIRMED. Уникальность `(order, kind)` гарантируется PostgreSQL. Получатель копируется из `Order.telegram_user_id`: телефон, username, Customer PK и Telegram ID сотрудника не используются. Первый этап, отмена, повторные callback и одновременные подтверждения не создают второе логическое уведомление.

`transaction.on_commit` запускает одну короткую попытку через существующий `telegram_call`. Сетевого вызова внутри транзакции подтверждения нет. Отказ, блокировка бота, тайм-аут или ошибка сохранения результата доставки не отменяют статус и аудит заказа. Функция выключена по умолчанию; после её включения старые уже подтверждённые заказы не обходятся и не получают рассылку. Подтверждение через ручное изменение статуса в Admin не создаёт личное уведомление: автоматический сценарий привязан к последнему этапу Telegram-подтверждения.

HTML безопасно экранируется, номер и время берутся из сохранённого заказа; дата форматируется по Europe/Moscow. Для старого NEW-заказа без pickup_at время не выдумывается, выводится «время уточняется оператором».

Кнопка «🛒 Посмотреть заказ» имеет `web_app.url = MINIAPP_PUBLIC_URL + /profile/orders/<public_id>`. Это обычный поддерживаемый Telegram механизм для личного чата пользователя с ботом, без токенов доступа в URL. Ссылка открывает существующий маршрут React; доступ к данным остаётся за текущей серверной Telegram-сессией. Чужой Telegram-пользователь получает 404 от API заказа. Работа HTTPS SPA-маршрута и это ограничение проверяются серверными тестами.

## Доставка и Django Admin

Новый раздел: **Витрина и заказы → Личные уведомления покупателям**. Показаны получатель, тип, статус, попытки, код ошибки, ID сообщения и ручная проверка. Изменять получателя/payload или добавлять записи через Admin нельзя.

- `pending`: есть сохранённая запись, попытку можно выполнить действием «Отправить одно ожидающее уведомление». В том числе после перезапуска Render до начала отправки.
- `sending`: запись захвачена одной попыткой на 120 секунд. Конкурентная попытка не отправляет сообщение. Истёкший lease переводится из Admin в `uncertain`, не обратно в очередь.
- `sent`: Telegram подтвердил ID сообщения в правильном личном чате, либо результат подтверждён ручной проверкой. Автоматической повторной отправки нет.
- `failed`: определённый отказ Telegram, например 403 (запрет личных сообщений/покупатель не начинал диалог) или 429. После устранения причины доступно «Повторить после определённого отказа Telegram». Для 429 действует пауза 60 секунд. Ошибки подготовки URL/получателя не вызывают сетевой запрос.
- `uncertain`: тайм-аут, 5xx, неизвестная ошибка, неполный ответ или сбой сохранения Telegram receipt. Прямой повтор запрещён. Через «Проверить неопределённую доставку» нужно уточнить результат у покупателя/по достоверной записи: «Получено» отмечает доставленным без отправки; «Не получено» разрешает один повтор. Сохраняются проверивший администратор, время и результат. Если результат выяснить нельзя, запись остаётся uncertain.

Payload и получатель замораживаются перед первой попыткой. При повторе они сохраняются; нельзя перенаправить сообщение другому пользователю. Для нового раздела сотрудникам без superuser нужны обычные view/change permissions. Действия Admin ограничены одним уведомлением, защищены штатной авторизацией и CSRF.

Нет Redis, Celery, бесконечного фонового процесса или платной рассылки. После неудачной/прерванной попытки требуется действие Admin. Выключение флага приостанавливает отправку из очереди и повторы; ручную фиксацию уже выясненного результата можно выполнить без отправки.

## Миграция

`0014_customerordernotification` создаёт только новую таблицу, индексы и FK на Order/администратора. Не изменяет существующие заказы, номера, товары, цены, профили, изображения или outbox рабочей группы. Нет RunPython/backfill. Тест MigrationExecutor на отдельной PostgreSQL проверяет сохранение ID/полей существующего заказа, group outbox, товара/пути изображения и отсутствие личных уведомлений для прежних CONFIRMED.

## Разрешённая публикация и Render

1. Дождаться зелёного CI. Перед согласованным Merge — свежая резервная копия существующим процессом проекта. Только по разрешению владельца Merge в staging; штатный Render применит 0014. При первом обновлении оставить личные уведомления выключенными.
2. Новый параметр: `TELEGRAM_CUSTOMER_NOTIFICATIONS_ENABLED=0` (значение по умолчанию в Django). В Blueprint он dashboard-managed через `sync: false`, поэтому последующий Sync не сбросит выбор владельца.
3. После проверки установить в Render → Environment **`TELEGRAM_CUSTOMER_NOTIFICATIONS_ENABLED=1`** и сохранить. Нужны уже существующий `TELEGRAM_BOT_TOKEN` и корректный постоянный `MINIAPP_PUBLIC_URL` (staging умеет использовать Render hostname). Токен, webhook, BotFather, `TELEGRAM_ADMIN_CHAT_ID` и флаги групповых уведомлений менять не нужно.
4. Для контрольной проверки покупатель должен открыть личный диалог с @bmmsev_bot и нажать Start либо ранее разрешить боту писать. Одного Telegram ID недостаточно для обхода запрета личных сообщений. Блокировку система фиксирует как ошибку, не меняя заказ. Разрешения не запрашиваются вместо авторизации Mini App.
5. Оформить согласованный контрольный заказ. На первом этапе личного сообщения нет; после второго — одно сообщение. Проверить номер, московское время и кнопку на настоящих Telegram iOS и Android, затем повторное нажатие сотрудника и состояние Admin. В Mini App остаются прежние статус, телефон и история.

При откате сначала поставить флаг в 0. Не удалять заполненную таблицу/миграцию вместе с историей доставки. Отдельной команды рассылки старых подтверждённых заказов нет.

## Проверки и ограничения

Новый серверный набор покрывает конечный этап/отмену, правильного покупателя, HTML/дату/кнопку, авторизацию владельца/чужого пользователя, повторы, rollback и внешний commit, блокировку бота, rate limit, неоднозначную отправку, потерю записи receipt после успеха, ручную проверку/повтор, отключённый флаг и истёкший lease. На изолированной PostgreSQL дополнительно проверяются два сотрудника, два отправителя и миграция.

Сообщения в тестах отправляются в mock Telegram API. Нативные iOS/Android и реальные личные сообщения ещё требуют проверки владельцем после разрешённого релиза. Не заявляется гарантированное системное push-уведомление или прочтение сообщения пользователем.

Протокол: [личные InlineKeyboardButton.web_app](https://core.telegram.org/bots/api#inlinekeyboardbutton), [sendMessage](https://core.telegram.org/bots/api#sendmessage), [Django on_commit](https://docs.djangoproject.com/en/6.0/topics/db/transactions/#performing-actions-after-commit).
